## Before you stand up

**The rate limit is 50 queries per hour, per IP.** This is the only thing that
can kill the demo. This script uses about 15. Do not rehearse the whole thing on
the venue wifi in the hour before you present — you will arrive with a spent
budget and a room full of 429s. Rehearse on a hotspot, or rehearse only the UI.

Check your headroom right before you start:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://beacon.afrigen-d.org/api/health
```

`200` and you are fine. `429` means wait, or change network.

**ARDI is down right now.** `beacon.ardi.africa` returns 530 direct; the network
sees HTTP 502 from it. So the fan-out reports 2 queried, 1 responded. Do not hide
it — it is the strongest moment in the demo and there are words for it below.

**Make the font big.** `Cmd +` several times. Nobody at the back can read 12pt
JSON.

## 0:00 — Open

> A Beacon answers one question: *do you have this variant?* — yes or no. No
> genotypes, no individuals, no data leaves the host. You discover **that** a
> cohort has something, then negotiate access separately. That is what makes it
> shareable when the data itself is not.
>
> And the thing I want to insist on before I show you anything: **a Beacon is
> not a website. It is a specification.** What you are about to see is the GA4GH
> Beacon v2 protocol. The web page I will show at the end is one client of it —
> ours, and the least important part of this. What matters is that any Beacon v2
> client works against this without knowing anything about AfriGen-D, and that
> this beacon joins any Beacon v2 network without either side writing
> integration code.
>
> That is why I am starting at a terminal. If I opened the browser first, you
> would reasonably conclude we had built a variant-lookup website. We did not.
> We implemented a standard, and the website is a thin thing on top that we
> could throw away tomorrow.

### Put the whole specification on screen

Show this while you talk. It is the entire Beacon v2 surface on one screen, with
what we serve marked — so the claim "this is a spec" is visible rather than
asserted.

```text
GA4GH BEACON v2  =  FRAMEWORK (the protocol)  +  MODELS (the biology)

FRAMEWORK — endpoints that describe the beacon itself
  GET /                     identity, organisation, description        [ours]
  GET /info                 same, alternate path                       [ours]
  GET /service-info         GA4GH-wide service discovery               [ours]
  GET /configuration        entry types, security levels, maturity     [ours]
  GET /entry_types          which entities this beacon serves          [ours]
  GET /map                  endpoint index, for a client it never met  [ours]
  GET /filtering_terms      ontology terms accepted as filters         [empty]

MODELS — seven entry types, and every one gets the SAME three patterns
                            /<type>   /<type>/{id}   /<type>/{id}/<other>
  dataset          /datasets    yes        yes             yes
  cohort           /cohorts     yes        yes              -
  individual       /individuals yes         -               -      [queryable]
  biosample        /biosamples  yes         -               -      [empty]
  run              /runs        yes         -               -      [empty]
  analysis         /analyses    yes         -               -      [empty]
  genomicVariation /g_variants  yes         -              yes     [42.3M rows]

  every one of those is GET *and* POST

GRANULARITY   boolean  <- what we serve      SECURITY   PUBLIC  <- ours
              count                                     REGISTERED
              record                                    CONTROLLED
```

> That is the whole thing. Six endpoints that describe the beacon, seven
> biological entity types, and a regular pattern repeated across all of them —
> list it, fetch one, or cross from one entity to another. Plus three levels of
> how much the beacon is willing to say, and three tiers of who is allowed to
> ask.
>
> We serve the boolean level, at the public tier, and two of the seven entity
> types properly. I would rather tell you that than imply we implement all of
> it. The point is not our coverage — the point is that **the shape is not ours
> to choose.** Every beacon in the world exposes these same paths, which is why
> a client written for one works against all of them.
>
> And notice the third column: `/<type>/{id}/<other-type>`. That is what makes
> this more than a variant lookup — you can walk from a variant to the
> biosamples carrying it to the individuals they came from, if you are
> authorised for that tier. We are not, today, and that is deliberate.

## 1:00 — Prove it is a spec, before asking it anything

### The endpoint map

**Why:** it is the single best evidence that this is a protocol and not a site.
**What it does:** `/map` is a required Beacon v2 endpoint whose entire job is to
tell a client it has never met what this beacon can be asked.

```bash
curl -s https://beacon.afrigen-d.org/api/map | jq '.response.endpointSets | keys'
```

```json
["cohorts", "datasets", "g_variants", "individuals"]
```

> I have told this thing nothing about my client. It is telling me what it
> accepts. Nobody wrote an adapter for me — the spec says the map is there, so
> it is there, and every conformant beacon in the world answers this same call.

### What it can be asked about

**Why:** to show it declares its own scope in the spec's vocabulary.
**What it does:** `/entry_types` lists which of the spec's biological entities
this beacon actually serves.

```bash
curl -s https://beacon.afrigen-d.org/api/entry_types | jq '.response.entryTypes | keys'
```

```json
["g_variants", "individuals"]
```

> Two of the spec's seven entity types. I am not claiming we implement all seven
> — the full list is in the appendix of this doc if anyone asks where we sit.

### Who it says it is

**Why:** so the room sees the identity and version the machine reports about
itself. **What it does:** `/service-info` is the GA4GH-wide service discovery
endpoint, used by every GA4GH service and not only Beacons.

```bash
curl -s https://beacon.afrigen-d.org/api/service-info | jq '.response | {id, name, organization: .organization.name, apiVersion}'
```

```json
{"id": "org.afrigen-d.beacon",
 "name": "GA4GH Beacon v2 - Public Discovery",
 "organization": "AfriGen-D",
 "apiVersion": "v2.0.0"}
```

> `apiVersion v2.0.0`. That string is in every response this thing gives,
> including its errors. A client reads it and knows exactly which contract it is
> talking to.
>
> **Use `jq '.response'` exactly as written.** Bare, it shows four nulls — those
> GA4GH fields sit inside the Beacon envelope rather than at the top level where
> a registry would look. Real gap on our side, on the fix list, not worth
> raising on stage. Just do not get caught by nulls on screen.

## 5:30 — The two things that make it a *good* beacon

### It knows hg38 and GRCh38 are the same genome

**Why:** this is the failure a beacon must never have, and we had it until three
weeks ago. **What it does:** the identical query using UCSC's name for the build
instead of the GRC's.

```bash
curl -s 'https://beacon.afrigen-d.org/api/g_variants?assemblyId=hg38&referenceName=1&start=55000000&end=55005000' | jq '.responseSummary'
```

```json
{"exists": true, "numTotalResults": 1}
```

> Same answer as GRCh38, because it is the same genome. Until three weeks ago
> this returned a confident **no** — and a wrong no is the worst thing a
> discovery service can do, because it is indistinguishable from a right one. A
> researcher would have concluded the variant was absent from African reference
> data and moved on.

### It refuses questions it cannot answer

**Why:** the design philosophy in a single response, and what makes the beacon
safe to publish from. **What it does:** asks for a genome build we hold no data
for.

```bash
curl -s 'https://beacon.afrigen-d.org/api/g_variants?assemblyId=GRCh37&referenceName=1&start=55000000&end=55005000' | jq '.error'
```

```json
{"errorCode": 501, "errorMessage": "This beacon holds no data for assembly GRCh37, so it cannot answer for that build. This is not a statement about whether the variant exists. Data held: GRCh38."}
```

> Read that last sentence — *this is not a statement about whether the variant
> exists*. We hold no GRCh37 data, so we return 501, I cannot answer, instead of
> `false`. "I cannot answer" and "the answer is no" are different statements,
> and only one of them is true here.

### It speaks the spec's own request format

**Why:** the second place to make the spec point — I did not design this request
body, the specification did. **What it does:** the same query as a POST, with
parameters nested the way a conformant client sends them.

```bash
curl -s -X POST https://beacon.afrigen-d.org/api/g_variants -H 'Content-Type: application/json' -d '{"query":{"requestParameters":{"assemblyId":"GRCh38","referenceName":"1","start":55000000,"end":55005000}}}' | jq '.responseSummary'
```

```json
{"exists": true, "numTotalResults": 1}
```

> Identical answer to the GET. I did not invent that body — `query`,
> `requestParameters`, nested exactly like that, is what the spec says a client
> sends. Nobody wrote an AfriGen-D adapter. If your tool speaks Beacon v2, it
> already speaks to this.

Not for the stage, but worth knowing: this returned 400 until three weeks ago. A
security filter was stringifying the nested object and matching its own
punctuation as an injection attempt. Every GET worked, so nothing looked broken
— and every spec-conformant client was refused.

### One query, fanned out

**Why:** this is the payoff — federation without moving data.
**What it does:** sends one query to the network, which asks every registered
beacon and aggregates the answers.

```bash
curl -s 'https://api-beacon-network-dev.afrigen-d.dev/api/g_variants?assemblyId=GRCh38&referenceName=1&start=55000000&end=55005000' | jq '{network, exists: .response.exists}'
```

```json
{"network": {"beaconsQueried": 2,
             "beaconsResponded": 2,
             "beaconsWithHits": 1,
             "beaconsNotQueried": 0},
 "exists": true}
```

> One question, two institutions, two countries. No data moved anywhere.
>
> And this is the third place I want to make the point: these two beacons were
> built by different teams, on different infrastructure, and nobody wrote an
> integration. The network queries both because both implement the same
> specification. If a Beacon were a website, federating it would be a project.
> Because it is a spec, federating it is configuration.

### The per-beacon breakdown — this is the moment

**Why:** the aggregate `exists: true` hides the interesting part — *which*
cohort has it. **What it does:** shows each beacon's own answer.

```bash
curl -s 'https://api-beacon-network-dev.afrigen-d.dev/api/g_variants?assemblyId=GRCh38&referenceName=1&start=55000000&end=55005000' | jq '.response.beaconResponses[] | {beaconName, status, exists}'
```

```text
{"beaconName": "ARDI Beacon (DDD-Africa DRC)", "status": "success", "exists": false}
{"beaconName": "AfriGen-D Beacon", "status": "success", "exists": true}
```

> Now look at that, because this is the whole argument for federating. Both
> beacons answered. The DRC cohort does **not** have anything at this locus.
> Ours does. Same question, two African cohorts, two different answers.
>
> That difference is the entire point. If you only queried one of these you
> would draw the wrong conclusion about African variation, and the only way to
> get both answers is to ask both — without either institution sending the
> other a single genotype.
>
> And notice: `beaconsWithHits: 1`. The network is telling me one of the two
> matched. It is not averaging them, and it is not hiding which.

### If ARDI is down when you run it

It was returning 502 at 10:12 this morning and healthy by 12:40, so you may get
either. If a beacon is unreachable the row looks like this instead:

```text
{"beaconName": "ARDI Beacon (DDD-Africa DRC)", "status": "error", "exists": null, "error": "HTTP 502"}
```

**This is just as good a demo — arguably better. Use these words:**

> One of the two is unreachable right now. That is a partner institution's host,
> not ours — and I am glad it happened, because look at what the network does
> with it. Two queried, one responded, and ARDI's row says `error` with
> `exists: null`.
>
> `null`, not `false`. It does not quietly report no hits and let me conclude
> the variant is absent from the DRC cohort. `null` means *we did not find out*.
> That distinction is the difference between a federation you can publish from
> and one you cannot — and in a real federation, someone is always down.

**The two cases make the same point from opposite directions:** working, it
shows you the disagreement between cohorts that is the reason to federate; down,
it shows you that the system knows the difference between "no" and "I could not
ask".

## Appendix — the Beacon v2 spec surface, and where we sit

Use this if someone asks "what else does the spec have?". Not part of the
15 minutes.

## Beacon v2 is two specifications

| | what it defines |
| --- | --- |
| **Framework** | the protocol — request/response envelope, the informational endpoints, granularity, filters, pagination, security tiers, handovers |
| **Models** | the biology — the entry types and their schemas |

## Framework: the informational endpoints

These describe the beacon rather than answering about data.

| Endpoint | What it is for | Ours |
| --- | --- | --- |
| `GET /` or `/info` | beacon identity, organisation, description | yes |
| `GET /service-info` | GA4GH-wide service discovery (not Beacon-specific) | yes, but nested in the envelope |
| `GET /configuration` | declared entry types, security levels, maturity | yes |
| `GET /entry_types` | which entities this beacon serves | yes |
| `GET /map` | endpoint index for an unknown client | yes |
| `GET /filtering_terms` | the ontology terms/filters accepted | routed, returns empty |

## Models: the seven entry types

| Entry type | Endpoint | Ours |
| --- | --- | --- |
| `dataset` | `/datasets` | yes, with counts |
| `cohort` | `/cohorts` | list + detail |
| `individual` | `/individuals` | queryable (sex, disease code) |
| `biosample` | `/biosamples` | routed, empty |
| `run` | `/runs` | routed, empty |
| `analysis` | `/analyses` | routed, empty |
| `genomicVariation` | `/g_variants` | **the real one** — 42.3M variants |

## The three endpoint patterns, per entry type

The spec is regular: every entry type gets the same three shapes, GET and POST.

| Pattern | Meaning |
| --- | --- |
| `/<entry-type>` | list, or query with parameters |
| `/<entry-type>/{id}` | one record by id |
| `/<entry-type>/{id}/<other-entry-type>` | cross-entity — "the biosamples of this individual" |

That third pattern is what makes a Beacon more than a variant lookup: you can
walk from a variant to the biosamples that carry it to the individuals they came
from, subject to the tier you are authorised for.

## Granularity — how much the beacon is willing to say

| Level | Response |
| --- | --- |
| `boolean` | yes/no only — **what we serve publicly** |
| `count` | how many matched |
| `record` | the matching records themselves |

## Security tiers

| Tier | Meaning |
| --- | --- |
| `PUBLIC` | anonymous — **ours** |
| `REGISTERED` | authenticated researcher |
| `CONTROLLED` | authorised for specific datasets, typically via GA4GH Passports |

We declare `PUBLIC` only. Registered and controlled tiers are not implemented —
which is the honest answer if anyone asks about controlled access.

## What the EGA verifier checks

`docs/verifier/beacon-verifier-2026-08-06.json`, run against
`https://beacon.afrigen-d.org/api/` — 11 entities, covering exactly the three
patterns above:

```text
Dataset all entries / single entry
Genomic Variants all entries / related with a Dataset
Individual all entries / related with a Dataset
Biological Sample all entries / related with a Dataset
Bioinformatics analysis all entries / related with a Dataset
Sequencing run all entries / related with a Dataset
Cohort all entries
```

**It checks envelope shape, not answer correctness.** It passed throughout the
period when `hg38` returned a confident wrong `no`. Worth knowing before quoting
a verifier score as evidence of anything.

## Our data models, for completeness

MongoEngine documents in `beacon_api/models.py`:

`Variant`, `VariantAnnotation`, `VariantInDataset`, `Individual`, `Biosample`,
`Analysis`, `Cohort`, `Dataset`, `FilteringTerm`, `QueryLog`

`VariantInDataset` is the join that lets one variant be attributed per dataset;
`QueryLog` is the audit trail, with client IPs truncated and a TTL.
